# AI 活动机会管理工具 PRD

## 1. 背景

用户经常从微信公众号、小红书、微信群、朋友圈、网页、截图等渠道看到 AI 活动、黑客松、比赛、讲座、训练营等机会。目前的保存方式主要是转发到个人微信群或临时收藏，导致信息分散、无法检索、无法自动提醒，也难以判断哪些活动真正值得投入时间。

本产品希望将零散活动信息转化为可确认、可筛选、可提醒、可追踪的结构化机会池。

## 2. 产品定位

本产品不是单纯的日历助手，而是一个面向个人的 AI 活动机会管理系统。

核心价值：

- 将微信推文、小红书笔记、截图、复制文本等非结构化内容转成活动卡片。
- 保留原文证据，避免 AI 提取结果失真。
- 帮助用户判断活动是否值得参加。
- 将确认后的报名截止、举办时间、赛程节点同步到日历或提醒系统。

一句话描述：

> 把散落在微信、小红书和截图里的 AI 活动信息，整理成可决策、可提醒、可追踪的机会看板。

## 3. 目标用户

### 3.1 核心用户

- 经常关注 AI 活动、黑客松、比赛、线下沙龙、训练营的个人用户。
- 希望通过活动积累作品集、人脉、项目经验或求职素材的学生、开发者、产品经理、独立创作者。

### 3.2 次级用户

- 需要整理行业活动信息的社群运营者。
- 需要为团队收集比赛、会议、招募机会的组织者。

## 4. 用户痛点

### 4.1 信息入口混乱

活动信息来自微信公众号、小红书、微信群、网页、海报截图等多种渠道，当前保存方式没有统一入口。

### 4.2 关键信息缺失或难找

活动正文中常常混杂宣传语、图片、二维码和长篇介绍。用户真正需要的是报名截止时间、举办时间、地点、链接、赛程等字段。

### 4.3 容易错过截止时间

报名截止、组队截止、初赛提交、决赛答辩等节点经常散落在正文或图片中，用户缺少自动提醒。

### 4.4 收藏不等于行动

用户保存了很多活动，但没有进一步判断是否值得参加，也没有形成后续行动。

### 4.5 原文证据丢失

微信公众号文章可能删除，小红书笔记可能隐藏，单纯保存链接不可靠。

## 5. 产品目标

### 5.1 MVP 目标

在第一版中，用户可以：

- 粘贴活动链接、正文或上传截图。
- 由 AI 自动提取活动结构化信息。
- 在人工确认后生成活动卡片。
- 按报名截止时间、举办时间、状态筛选活动。
- 为确认参加或感兴趣的活动创建提醒或导出日历。

### 5.2 非目标

第一版不做：

- 微信群消息全自动监听。
- 小红书和微信公众号大规模自动爬取。
- 完整团队协作系统。
- 复杂推荐算法。
- 面向公开用户的活动广场。

这些能力会显著增加平台风控、隐私、安全和维护成本，不适合作为 MVP 起点。

## 6. 核心场景

### 6.1 保存微信公众号活动推文

用户复制微信公众号文章链接或正文，粘贴到工具中。系统提取活动名称、报名链接、报名截止时间、举办时间、地点和赛程。用户确认后保存到活动库。

### 6.2 保存小红书活动笔记

用户复制小红书笔记链接、正文，或上传截图。系统提取关键信息。如果链接内容无法读取，则允许用户通过截图或复制正文完成录入。

### 6.3 从海报截图中提取活动

用户上传活动海报截图。系统通过 OCR 和视觉模型提取文字，再生成活动卡片。

### 6.4 判断是否参加

系统根据用户目标和活动信息生成参考判断，包括匹配度、时间成本、作品集价值、人脉价值、紧急程度和建议理由。用户最终决定状态。

### 6.5 同步提醒

用户将活动标记为“想参加”或“已报名”后，系统为报名截止、活动开始、关键赛程节点生成提醒。

## 7. 用户流程

```text
收集内容
  -> AI 提取
  -> 进入待确认
  -> 用户修正字段
  -> 保存为活动卡片
  -> 用户判断状态
  -> 生成提醒/日历事件
  -> 活动结束后归档
```

## 8. 功能需求

### 8.1 内容收集

#### 8.1.1 输入类型

必须支持：

- 粘贴纯文本。
- 粘贴微信公众号文章链接。
- 粘贴小红书笔记链接。
- 上传截图或海报图片。
- 手动新建活动。

后续支持：

- 浏览器插件保存当前页面。
- 手机分享菜单。
- Telegram Bot 或企业微信 Bot。
- Notion/飞书数据库同步。

#### 8.1.2 原文保存

每条内容必须保存：

- 来源平台。
- 原始链接。
- 原始文本。
- 上传图片。
- 抓取时间。
- 发布时间，如果可获得。
- 解析状态。

### 8.2 AI 信息抽取

系统需要从原始内容中提取以下字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| 活动名称 | 是 | 活动/比赛/黑客松名称 |
| 活动类型 | 否 | 黑客松、比赛、沙龙、训练营、会议等 |
| 主办方 | 否 | 组织者或承办方 |
| 来源平台 | 是 | 微信、小红书、网页、截图、手动 |
| 原文链接 | 否 | 可回溯链接 |
| 报名链接 | 否 | 表单、二维码说明或官网链接 |
| 报名开始时间 | 否 | 可为空 |
| 报名截止时间 | 否 | 关键提醒字段 |
| 活动开始时间 | 否 | 举办开始时间 |
| 活动结束时间 | 否 | 举办结束时间 |
| 举办地点 | 否 | 城市、场馆、线上平台 |
| 是否线上 | 否 | 线上、线下、混合 |
| 赛程安排 | 否 | 报名、初赛、复赛、决赛等节点 |
| 费用 | 否 | 免费、付费、押金等 |
| 奖励 | 否 | 奖金、证书、资源、孵化等 |
| 组队要求 | 否 | 是否需要组队、人数限制 |
| 适合人群 | 否 | 学生、开发者、创业者等 |
| 缺失字段 | 是 | AI 认为需要用户补充的信息 |

### 8.3 字段级证据

每个关键字段需要保存证据：

```json
{
  "field": "registration_deadline_at",
  "value": "2026-06-01T23:59:00+08:00",
  "evidence": "报名截止时间：6月1日 23:59",
  "confidence": 0.92
}
```

关键字段包括：

- 报名截止时间。
- 活动开始时间。
- 活动结束时间。
- 举办地点。
- 报名链接。
- 费用。
- 组队要求。

### 8.4 相对时间处理

系统必须识别相对时间表达：

- 今天、明天、后天。
- 本周五、下周一。
- 月底前。
- 今晚、明晚。
- 报名截止至本月底。

转换相对时间时必须结合：

- 当前解析时间。
- 文章发布时间。
- 用户所在时区，默认 `Asia/Shanghai`。

如果无法确定具体日期，系统不得强行猜测，应标记为“需要确认”。

### 8.5 待确认队列

AI 提取后的活动必须先进入待确认队列，不能直接写入正式活动库。

待确认页需要支持：

- 查看原文和提取结果。
- 编辑字段。
- 接受 AI 建议。
- 标记字段错误。
- 放弃该条内容。
- 合并到已有活动。

### 8.6 活动状态

活动状态包括：

- `inbox`：已收集，未解析。
- `extracted`：已解析，待确认。
- `needs_review`：关键信息缺失，需要人工确认。
- `interested`：感兴趣。
- `applied`：已报名。
- `rejected`：已放弃。
- `expired`：已过报名截止。
- `ongoing`：正在进行。
- `done`：已结束。

### 8.7 机会评分

系统为每个活动生成参考评分，但最终决策由用户决定。

评分维度：

| 字段 | 说明 |
|---|---|
| fit_score | 与用户目标和兴趣方向的匹配度 |
| urgency_score | 截止时间紧急程度 |
| portfolio_value | 对作品集或简历的价值 |
| networking_value | 人脉、资源、曝光价值 |
| learning_value | 学习价值 |
| time_cost | 时间成本 |
| recommendation | 建议参加、观望、放弃 |
| reason_to_join | 建议参加理由 |
| reason_to_skip | 建议放弃理由 |

第一版允许用户手动填写个人目标，例如：

- 我关注 AI Agent、AI 编程、产品设计。
- 我希望积累作品集。
- 我不想参加纯营销性质活动。
- 我只能参加线上或周末活动。

### 8.8 提醒与日历

提醒类型：

- 报名截止前 3 天。
- 报名截止当天。
- 活动开始前 1 天。
- 赛程节点前 1 天。
- 用户自定义提醒。

日历事件类型：

- 报名截止。
- 活动举办时间。
- 赛程节点。

原则：

- 只有用户标记为 `interested` 或 `applied` 的活动才默认生成提醒。
- `inbox`、`extracted`、`rejected` 状态不进入日历。
- 日历不是数据库，不能塞入所有收集到的活动。

### 8.9 去重与合并

系统需要识别重复活动：

- 活动名称相似。
- 主办方相同。
- 报名链接相同。
- 举办时间相同。
- 原文链接不同但活动主体一致。

重复活动处理方式：

- 提示用户合并。
- 保留多个来源证据。
- 用置信度更高的信息补全缺失字段。
- 保留冲突字段供用户选择。

### 8.10 搜索与筛选

必须支持：

- 按关键词搜索。
- 按活动状态筛选。
- 按报名截止时间排序。
- 按活动类型筛选。
- 按线上/线下筛选。
- 按城市筛选。
- 按机会评分排序。

## 9. 页面设计

### 9.1 Inbox 页面

用途：承接所有未处理内容。

核心元素：

- 新建输入框。
- 链接/文本粘贴区。
- 图片上传。
- 原始内容列表。
- 解析状态。

### 9.2 Review Queue 页面

用途：人工确认 AI 提取结果。

核心元素：

- 左侧原文/截图。
- 中间结构化字段。
- 右侧 AI 证据和置信度。
- 确认、放弃、合并按钮。

### 9.3 Activities 页面

用途：活动机会看板。

视图：

- 列表视图。
- 看板视图。
- 日历视图。

核心字段：

- 活动名称。
- 报名截止。
- 举办时间。
- 状态。
- 评分。
- 下一步行动。

### 9.4 Activity Detail 页面

用途：查看单个活动详情。

模块：

- 基础信息。
- 时间节点。
- 报名信息。
- 原文证据。
- AI 评分。
- 用户笔记。
- 提醒设置。

### 9.5 Brief 页面

用途：每日或每周机会简报。

内容：

- 即将截止的活动。
- 推荐优先处理的活动。
- 信息缺失需要确认的活动。
- 已过期但未处理的活动。

## 12. 成功指标

### 12.1 使用指标

- 每周收集活动数量。
- AI 成功提取率。
- 待确认转正式活动比例。
- 生成提醒的活动比例。
- 用户手动修正字段次数。

### 12.2 结果指标

- 报名截止错过次数下降。
- 用户实际报名活动数量。
- 用户放弃低价值活动数量。
- 用户每周处理活动信息的时间减少。

### 12.3 质量指标

- 报名截止时间提取准确率。
- 活动举办时间提取准确率。
- 报名链接提取准确率。
- 重复活动识别准确率。

## 13. 风险与约束

### 13.1 平台限制

微信公众号和小红书存在登录态、反爬、链接失效、内容不可访问等问题。第一版应以用户主动粘贴、上传和分享为主。

### 13.2 AI 幻觉

AI 可能误读时间、地点、报名链接。必须保留证据和人工确认流程。

### 13.3 日历污染

如果所有收集内容都写入日历，用户会快速失去信任。必须只同步用户确认后的活动。

### 13.4 信息过载

如果产品只增加收集能力，不增加筛选和决策能力，会让用户更焦虑。因此机会评分和状态流转是核心能力，不是锦上添花。

### 13.5 隐私安全

用户保存的链接、截图和笔记可能包含私人信息。需要明确本地优先或私有存储策略。

## 14. 推荐技术路线

### 14.1 MVP 技术栈

- 后端：Python + FastAPI。
- 包管理：uv。
- 数据库：SQLite 起步，后续可迁移 PostgreSQL。
- 前端：React 或 Vue。
- OCR：可先使用多模态模型处理截图。
- AI 抽取：结构化 JSON 输出，配合字段校验。
- 日历：先支持 ICS 导出，再考虑 Google Calendar API。

### 14.2 可复用外部组件

- 微信公众号文章下载：OpenCLI WeChat。
- 小红书读取：xiaohongshu-cli、redbook 或 xhs-mcp。
- 原文仓库参考：Karakeep、Linkwarden。
- 自动化工作流参考：n8n。
- Notion 日历同步参考：SyncNotionGoogleCalendar。

## 16. 开放问题

- 第一版主存储选 Notion/飞书，还是自建数据库？
- 用户是否需要手机端优先？
- 提醒渠道优先选择日历、微信、邮件还是桌面通知？
- 是否需要支持团队或社群共享活动库？
- 用户的个人目标应该如何配置，才能让机会评分真正有用？

## 17. 产品原则

- 先可靠，再自动。
- 先确认，再提醒。
- 先保存证据，再相信结论。
- 日历只放行动，不放收藏。
- 工具的目标不是收集更多活动，而是帮助用户更少错过、更快判断、更好行动。
