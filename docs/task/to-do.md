### T-008 微信链接抓取可用性

- 优先级/状态：P0 / `done`（定向回归 + 真实文章抽样验收）；依赖：T-001 的严格校验与配置契约。

- 边界：`wechat_fetcher.py` 的响应体限制与标题提取、前端链接类型判定；不改严格 host 校验、不放宽分享入口、不改数据库与依赖。
- verify：真实文章体量（传输小、解压后大）不被误杀；传输预检和解压上限各自独立生效；高压缩比响应仍受硬上限约束；标题在 `<title>` 为空时仍能取到；前后端链接判定一致。
- 风险/回滚：不降低 SSRF 防护强度；保留粘贴补全路径作为兜底。
- 定位（2026-10-23）：用 11 个真实公开文章链接抽样，发现两个既有缺陷。
  1. **响应体上限误杀真实文章**：原实现把 2 MiB 同时当作传输上限与解压后上限。实测真实文章 gzip 传输约 0.78 MiB，但**解压后 2.46~3.52 MiB**，体积几乎全部来自内联脚本与样式（正文仅几十 KB）。11 个样本中 9 个解压后超过 2 MiB，被判为「文章响应超过 2 MiB」，正文根本没进入解析。这不是边缘情况，是常态失败。
  2. **标题提取失效**：真实微信页面的 `<title>` 标签是**空**的，标题只在 `og:title` meta 中。原实现只认内嵌 JSON 的 `"title":` 和 `<title>` 标签，取不到就退化成「未命名文章」，用户在 Inbox 里认不出条目。
  3. **前后端链接判定不一致**：前端用 `includes('mp.weixin.qq.com')` 子串匹配，后端用严格 host 校验。`https://evil.com/?x=mp.weixin.qq.com` 会被前端送去抓取接口，再被后端按非法链接拒绝，用户看到的是误导性错误。
- 实现边界：[微信抓取器](../../backend/app/services/wechat_fetcher.py) 拆分 `MAX_WIRE_BYTES`（传输预检，4 MiB）与 `MAX_DECOMPRESSED_BYTES`（解压后硬上限，8 MiB）；`iter_content` 给出的是解压后字节，故按解压口径限制。上限取值基于 11 个真实样本的实测分布（最大 3.52 MiB），留约 2 倍余量。新增 [链接规则模块](../../frontend/src/link-rules.ts) 供前端判定，与后端 `is_wechat_url` 规则逐条对齐（含 `:443`、无用户信息、`/s/<id>` 与 `/s?__biz/mid/idx` 两种形态）。
- 实际验证：`pytest tests/test_t001_ingest.py -q` → **80 passed**（新增 6 项：真实体量文章可解析、声明长度超限仍在读正文前拒绝、解压后仍有硬上限、gzip 炸弹仍受控、`og:title` 两种属性顺序）。合并 T-001/T-002/T-003 五个文件 → **219 passed**。前端 `node --test tests/link-rules.test.cjs tests/time-ui.test.cjs tests/activity-details.test.cjs` → **13 passed**，其中前后端判定一致性用 19 个用例逐条比对。`npm.cmd run build`（含 tsc）通过。Ruff 对改动文件仅剩 **2 项既有 E501**（正文解析代码，与 `HEAD` 对照确认非本次引入），差异空白检查通过。
- 真实文章抽样验收（受控外网，9 个公开活动文章链接）：修复前 **0/9** 能抓到正文（全部被 2 MiB 上限拦截）；修复后 **7/9** 标题与正文完整可用，余 2 个为微信风控的偶发响应（同一链接重试即成功，单独立即抓取正常），非代码缺陷。抽样同时确认 `Content-Length` 声明值约 0.78 MiB、解压后 2.46~3.52 MiB、`js_content` 位于文档前 15%。
