# Planbox 技术与制作规范

更新：2026-10-16。适用于后续增量实现与审查。文中“必须”是本项目的验收要求；现有代码的缺口进入待办，不能因本文件存在就声称已经落实。参考来源与日期见 [references](references.md)。

## 1. 技术选型与升级策略

继续使用模块化单体。前后端与已有数据模型可分职责演进，不为当前个人工具引入微服务。目标是新来源、新模型和新评价规则能在明确边界内增加，并能独立验证。

下列是当前配置/锁文件事实，不是“全网最新版本”或生产环境版本。Python 声明要求 `>=3.11`；当前本地环境曾出现解释器元信息版本不一致警告，尚未在本轮重建环境。

| 层 | 当前锁定版本 | 下一阶段选择与理由 |
| --- | --- | --- |
| 前端 | React/React DOM 19.2.6、TypeScript 5.9.3、Vite 7.3.3、lucide-react 0.468.0 | 保留；已有 strict 与构建基础，先修流程和状态归属 |
| API/校验 | FastAPI 0.136.1、Pydantic 2.13.4、pydantic-settings 2.14.1 | 保留；明确请求、结果和配置契约 |
| 网络/服务 | httpx 0.28.1、requests 2.34.2、Uvicorn 0.47.0 | 保留现状；新增异步外部边界优先使用已有 httpx，旧同步抓取在触及时局部处理 |
| 数据 | SQLite / Python sqlite3 | 适合当前单人验证；约束、事务、迁移、备份先补齐；不把容器内文件当作持久化证明 |
| 质量工具 | pytest 9.0.3、Ruff 0.15.13；前端现有 tsc/Vite | 保留；pytest 已在锁文件但现有根测试脚本不能直接全量收集，先规范测试入口 |
| 模型 | 自有 Provider 抽象与兼容 Chat Completions 接口 | 保留适配边界；文本/视觉能力、模型版本与真实配置逐项核验；不固定承诺某家模型效果 |
| 排期 | 尚未实现 | 先用可测试的确定性约束与规则；模型给任务草案和解释，排期可重算 |
| 日历 | 自有 ICS 导出 | 保留兼容；内部时间表优先，外部 OAuth 与同步后置 |

增加 ORM、PostgreSQL、队列、状态管理库、Agent 框架或向量库前，必须说明当前代码阻碍、具体收益、替代方案、运行成本和迁移/回滚方式。无关的技术更新不混入功能提交。

## 2. 模块职责与依赖

```text
UI → API 请求/响应契约 → 用例服务 → 领域规则
                                 → Repository / 来源适配器 / 模型 Provider
领域规则不依赖 HTTP、React、SQLite 或厂商 SDK。
```

| 模块 | 负责 | 边界要求 |
| --- | --- | --- |
| API/router | 输入校验、错误映射、调用用例 | 不写抓取、评分或排期算法，不直接拼业务 SQL |
| SourceAdapter | 平台链接、正文/图片和来源元数据 | 返回统一结果与失败原因；不决定参加与否 |
| Extraction | 从内容生成候选、证据和未知项 | 不直接创建已确认活动或写日历 |
| OpportunityAssessment | 按目标与个人约束评价可参加性、价值与差距 | 不将不同目标总分直接混比；不执行报名 |
| TaskDrafting | 从选定机会拆准备任务和估时 | 明确估计与主办方事实，不编造要求 |
| Planning | 检查依赖、容量、时间块及未排原因 | 不改主办方截止，不静默覆盖锁定安排 |
| Repository/事务入口 | 查询、持久化、约束、用例事务 | 多次业务写入共享明确的事务边界，不各自提前 commit |
| Provider | 模型协议、超时、返回解析、用量 | 厂商参数留在适配层；结果必须经过领域校验 |

这些是目标职责，不表示所有模块已经存在。延续现有 `api/services/repositories/providers/schemas`，随任务增量形成边界。接口用于稳定的外部变化或测试替身，不给每个一次性函数套 BaseService/Factory。

建议前端按业务区域逐步组织 `features/inbox`、`review`、`opportunities`、`planning`，共享请求层和真正复用的 UI。只在相关任务触及且需要时拆分 App；不以任意行数或目录数量作为架构优劣指标。

## 3. 数据契约、证据与版本

- 来源、抽取候选、正式活动、目标评估、准备任务和计划是不同对象；固定举办时间与可调整准备任务分开。
- 外部数据进入时做运行时校验；状态使用封闭枚举和明确迁移，不接受任意字符串。
- `null` 表示未知，空列表表示已知没有结果；失败不能伪装成“没有活动”。需要时返回明确的处理中、需补全或失败状态。
- 同一来源支持多个候选；同一活动支持多个来源。冲突需保留双方依据，不以最大置信度自动选真相。
- 每个关键字段可追溯到来源与原文片段/图片位置；不能定位时标记未证实。模型 confidence 不作为校准概率，不用固定值制造精度。
- 人工更正记录旧值、新值、修改主体/时间和生效关系；历史依据可回看。只对已确认的事实参与可靠排期。
- 评估绑定活动内容、目标和个人约束的版本；任一输入改变应使相关旧结果过期。计划也有输入版本和确认版本，迟到响应不得覆盖新选择。
- SQL 参数化，排序/列名使用白名单；数据库操作不接收任意客户端列名。

## 4. 日期、时区、ICS 与排期

已确定的精确时刻使用 RFC 3339 表达，内部比较按实际时间统一，不比较带不同偏移的原始字符串。默认展示时区可用 Asia/Shanghai，但需显式保存和允许未来变更。

只有日期的内容保留 date 语义；相对时间保存参照时间及来源，年份缺失或依据冲突时进入待核对。不能把所有日期统一补 23:59 当作事实。验证日历真实性、开始/结束顺序、截止与任务依赖。

ICS 遵循 RFC 5545：CRLF、文本转义、稳定 UID、全日日期与精确时间语义、时区转换、建议的长行折叠；UTF-8 折叠不得切断字符。是否附 VALARM 与真实客户端是否提示分别验收。重复导出不应无说明地重复建项；文件导入不是实时同步承诺。

排期不变量：允许时段内、无资源冲突、前置先完成、真实截止前可完成、符合用户时长与缓冲限制、锁定安排保留。排不下返回原因和可选取舍；估时不足或长期容量未知时给有条件计划，不能声称现实中一定可完成或算法保证全局最优。

## 5. API 与错误

- 继续使用已有 FastAPI/OpenAPI；请求、响应和业务错误有稳定 schema。新接口采用明确的资源语义，集合有排序、分页及上限。
- 请求格式错误、业务约束、版本冲突、第三方暂不可用和内部异常分别说明；4xx/5xx 与返回内容一致。
- 新错误契约参考 RFC 9457，可提供 `type/title/status/detail/instance` 与业务错误码、request_id。旧 `detail` 消费端先做兼容，不能为统一格式破坏现有客户端。
- 报错不能返回 Token、Cookie、原始异常栈或私人原文。第三方提取失败不等于来源保存失败，结果分别表达。
- 有副作用的确认、合并、提取提交、计划确认应定义幂等键或等效唯一约束和冲突行为；网络重试不能产生重复活动与重复计划。
- 长操作可提供持久任务状态和重试入口；只有实际出现响应时间、恢复性问题后再增加工作队列，不能依赖进程内 BackgroundTasks 保证任务不丢。

## 6. 平台访问、模型与文件安全

- 外部链接与文档内容始终作为数据，不允许它们改变系统规则、用户目标或授权。
- URL 严格解析协议和 host；阻止用户信息段、危险端口/协议、内网/回环/链路本地等目标。短链和每次重定向都重新校验；限制跳数、超时、字节数和内容类型。
- DNS 解析和实际连接需保持一致，必要时使用受控网络出口，不能只查一遍字符串或 DNS 后任意连接。来源/图片 URL 也遵守同样规则。
- 平台登录只在明确用途和适用授权下进行。凭据不进源码、返回值、日志、协作记录；不自动扩大到评论、发布、付款或报名。
- 上传分层限制实际字节数、MIME/扩展名/文件特征、图片尺寸与像素量，受控生成文件名；不要仅信任 Content-Length。超限时内存、磁盘和响应行为均需测试。
- 用户原文、截图和忙闲最小化发送给模型；Provider 超时、限流、无效 JSON、字段错误都有有限处理和清楚状态。无法恢复的失败不能无限重试。
- 真实评估前写明请求上限、重试、失败停止条件；执行后记录次数、模型/提示/schema 版本及可获得的 Token。请求上限不是人民币费用上限。

模型使用遵循用户已有授权，包括适用的小规模 StepFun 测试授权；没有现成适用授权的充值、套餐购买、规模扩张或额外敏感数据发送仍需用户决定。本规范不要求对已授权测试逐轮重新确认。

## 7. 持久化、事务与恢复

SQLite 连接显式启用并验证外键；启用前检查旧孤儿数据。确认、合并等用例的写入在单事务内，错误可回滚；并发正确性依赖约束和原子写入，不能依赖“请求通常按顺序到达”。

迁移使用有序、可核验的版本记录；保留旧数据兼容说明、备份与恢复路径，避免散落的无记录自动改表。锁冲突优先缩短写事务并复现原因；WAL 等选项需基于并发与存储环境测量，不能替代事务设计。

文件与数据库生命周期一致：上传写入失败不留伪记录，数据库失败清理本次孤儿文件，删除/合并行为有明确恢复边界。备份应包含原文资产与数据库，并在临时副本做恢复检查。

本地存储不等于离线或零外发：调用模型仍可能发送内容。公网多用户使用前必须独立通过鉴权、对象归属、访问控制、配额、持久存储和恢复验证；CORS 不能替代鉴权。

## 8. 前端与制作验收

- 主要动作清楚：收集、核对、比较、选定、规划；每页有加载、空、失败、需补全、处理中、成功反馈。错误状态不写成无数据。
- Review 可编辑、看证据、保存与撤回；事实确认不自动等于报名或参加。来源不可读时给明确补全入口。
- 按实体 ID、目标 ID 和查询条件归属数据；证据、筛选列表与 Brief/规划各自有明确范围。避免复制可计算状态，处理乱序请求和旧响应。
- 保持 TypeScript strict；减少重复 DTO 和任意 `as` 断言。仅真正出现契约漂移时再评估类型生成工具，不手工再维护第三份 schema。
- 布局、颜色、间距与字号使用现有 design tokens；复用可访问的基础控件，不用绝对坐标拼页面，不让色彩成为唯一状态信号。
- 以 WCAG 2.2 AA 为目标：可见标签、键盘路径、焦点、对比度、错误关联与状态通知；触控与窄屏保留主要操作。自动检查之外需要键盘和实际浏览器验证，不宣称已完成全面符合性审计。
- 提交 UI 结果需检查真实渲染和用户可见行为；截图标明环境及真实/合成数据，源码推断不能写成运行截图。

## 9. 详细注释与避免冗余

公共接口、用例、适配器、复杂日期/去重/排期逻辑必须有中文 docstring/JSDoc，必要标识符保留英文。根据 PEP 257，说明行为、输入输出、可空性、时间单位/时区、异常与限制、持久化/网络副作用；必要时给一条短示例。

行内注释重点说明：为什么这样判断、外部平台限制、状态不变量、兼容原因、失败后的处理。算法注释写输入假设、约束、复杂度与不保证的内容。注释随逻辑同步修改。

```python
# 说明示例，不是本项目已实现代码。
# 截止原文缺少年份且没有可信发布时间时，保留待核对状态。
# 若直接套用当前年份，跨年报名可能被错误判为已经过期。
```

避免逐行复述赋值与循环、无依据的“高性能/智能”形容词、复制粘贴的冗长模板。短而自解释的内部函数可用精炼说明；“详细”以交接者能判断契约与风险为准，不以注释行数为准。TODO 注释引用 T/N/Q 编号、触发条件和清理条件。

共享重复的业务规则与外部调用边界，不把偶然相似的两段代码强行抽象。禁止无调用的预备模块、重复缓存/状态、宽泛捕获后假成功、为通过测试跳过断言，以及没有需求的全局重构。

## 10. 测试、可观察性与提交门禁

验证按风险分层：纯规则/时间/排期单元测试；SQLite 临时真实库的服务集成与并发；Provider/SourceAdapter 契约和异常替身；Review/排序/计划的浏览器流程；真实模型小样本单独评估。

当前 `test_e2e.py` 顶层执行 HTTP 请求与清库，**不要直接运行全仓 pytest**；T-007 先提供隔离与可重复入口，再启用新测试布局。现有 `test_server.py` 会重建 `.testdata/e2e.db`，运行前确认测试端口无人占用、路径确为测试库且其中无需保留内容。

日常启动与检查参考（从项目根，依赖安装/同步会改变本地环境，按需要执行）：

```powershell
uv sync --locked
uv run --locked python -m uvicorn backend.app.main:app --reload
# 检查，不自动修复或升级
uv run --locked python -m ruff check .
# 前端在 frontend 目录执行 npm.cmd ci 和 npm.cmd run build
```

`uv run --frozen --no-sync` 只可用于已核验环境的受控检查；它跳过同步，不能长期用来掩盖环境漂移。真实模型质量、浏览器体验与 CI 按各自环境记录，不能用本地命令成功替代全部结论。

日志记录 request/job/source/plan 标识、步骤、错误码、耗时、次数和可获得用量；不默认打印原文、图片、个人日程或凭据。发布前验证日志中可追踪失败且已脱敏。

每次提交检查 status、完整 diff、文件范围及验证结果；阶段性提交可独立审查和回滚。历史 SHA/测试证据保留，失败如实记录；有重大未解决缺陷不标任务 done。新增 CI 时锁版本和隔离数据，禁止在 CI 打真实凭据或默认付费调用。

## 11. 规范更新与完成定义

实现完成至少要能回答：需求经过哪些层、实际改了哪些层、未修改的相关层为何无需动、验证覆盖什么、哪些结果未验证、怎样恢复。文档任务只做本地链接、结构、事实与 diff 检查，无需为不变的业务代码反复运行高资源测试。

新任务遵循本规范；存量风险按 [to do](to-do.md) 收敛。若规范不适合具体场景，记录原因、替代方案和验证，不机械增加复杂度。新增长期规则应来自重复问题或清楚约束，能用测试/lint/CI 检查的规则逐步自动化。
